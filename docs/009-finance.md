# 009 — Finance

## Scope (MVP)
Invoices, fee structures (per class, with discount/scholarship overrides per
student), payment recording, receipts, outstanding-balance reporting.
Payroll is a separate, deliberately simple sub-module (staff salary
structure, payslip generation, leave tracking) — no PAYE/pension remittance
automation at launch, see the PRD's scope decision.

## Fee structure
Defined per class per term (e.g. "SS2 — Term 1: ₦45,000 tuition + ₦5,000
PTA levy"), with per-student overrides for discounts/scholarships/
installment plans. Generating a term's invoices for a class is a single
bulk action, not one-by-one.

## Payment collection
Paystack integration, two paths:
- **Monthly/Annual platform subscription** (Cognitio's own billing to the
  school) uses Paystack's native recurring Plan/Subscription intervals.
- **Termly platform billing** and **all school-fee collection from
  parents** uses one-time Paystack transactions/invoices — Paystack has no
  native "termly" interval, and school fee due-dates vary by
  school/session anyway, so this is generated by our own scheduler against
  each school's actual term dates, not forced into a fixed calendar cycle
  (full reasoning in the pricing decision log).

## Idempotency (critical — see 019)
Every payment-initiating action carries a client-generated idempotency key.
A double-tapped "Pay now" button, or a retried webhook from Paystack, must
never create two receipts for one payment. Enforced via a unique constraint
on `(school_id, idempotency_key)` at the database level, not just
application logic.

## Reporting
Outstanding fees by class/student, collection-rate trend, a debtor list the
Finance dashboard and Principal dashboard both read from the same
aggregation query (avoids the two dashboards ever showing different
numbers for the same thing).

## Status
Built: fee structure CRUD, idempotent payment recording (manual + a
signature-verified Paystack webhook — both funneling through one
conflict-safe path, using a SAVEPOINT rather than a full transaction
rollback on a duplicate idempotency key, after a real bug was caught
where the original code rolled back the entire session transaction, not
just the failed insert), and bulk invoice generation
(`POST /finance/invoices/generate` — sums a class's fee structure into
one invoice per enrolled student, skips students already invoiced so
it's safe to re-run). Frontend: the Finance screen (invoice list, status
filtering) and the Fee Structure setup screen with a one-click "generate
invoices" action per class/term.

Not yet built: a real "record payment" UI (the Finance screen
deliberately does not wire a payment button to a fake ₦0 amount — it
needs a proper amount-entry dialog first), and the Paystack payment-link
generation step itself (the webhook handler exists; nothing yet
generates the actual payment link a parent would click).
